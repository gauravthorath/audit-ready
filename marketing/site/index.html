Every verdict cites the record it came from, or it isn't a verdict.

AuditReady reads the tickets, change records and email threads you already have, tests them against a checklist standard, and returns a per-control readiness report where each finding is anchored to a specific record and timestamp. What it can't verify, it hands to a human instead of guessing.

Built and evaluated on a synthetic corpus of 20 tickets against 15 controls. The numbers below describe the method, not a production deployment - and the section on what this tool is not is as detailed as the rest of the page.

01 The problem

Audit prep is a filing exercise dressed up as a judgement call.

Before a certification audit, somebody has to walk every applicable clause and answer one question repeatedly: can we show this? The evidence already exists - it's scattered across a ticket system, a change log, and eighteen months of email. The work is finding it, deciding whether it actually satisfies the clause, and being able to point at it when an auditor asks.

The obvious move is to point a language model at the records and ask for a summary. That fails an audit for a specific reason: a summary is not evidence. An auditor doesn't want a paragraph saying change control looks fine. They want the change record, its approver, and the date - and if the model invented any of those, the finding is worse than useless, because someone acted on it.

So the constraint came first, before any of the architecture: no citation, no verdict. A verdict that can't resolve to a real record in the corpus is discarded by the pipeline, not shown with a caveat.

02 How it works

Retrieve, judge, then check the judge.

Each control is assessed by a small state machine, one control at a time. Retrieval is scoped to the ticket under review and joins linked change and email records by their identifiers rather than hoping semantic search finds them. The judge returns a verdict with citations. A separate verifier then re-reads the rubric condition by condition and states its own conclusion - it is never shown the judge's verdict first, because a verifier that sees the answer agrees with it.

Citations are resolved, not trusted

Every citation is checked against the corpus. One that points at a record or timestamp that doesn't exist invalidates the verdict rather than appearing as a footnote.

Standards are data, not code

A standard is a YAML file of controls and own-worded rubric conditions. Adding ISO 27001 alongside ISO 9001 took zero Python changes - the report picker found it by path.

Evidence arrives through one interface

Three live connectors behind one record shape: GitHub Issues over MCP, Jira over its REST API, Linear over GraphQL. Exported mail (.eml / .mbox) imports and links to tickets; CSV and JSON import work offline. Every connector's output is sanitised before a prompt sees it.

Evidence is snapshotted before it's judged

A run is pinned to the evidence as it stood, with provenance recording where each record came from and what the source could not supply. A finding you can't reproduce isn't defensible.

03 Calibration

The useful behaviour isn't accuracy. It's declining to answer.

When the verifier objects, the judge gets one more attempt with the objection in hand. If the verdict flips under review, it is never finalized - it goes to a review queue with the disagreement attached. On the labelled set that happened to 7 of 68 pairs.

The trade is explicit: agreement across everything it was asked is 0.941, but agreement on what it was willing to finalize is 0.984. It buys that by sending a tenth of the work to a person.

04 Evaluation

Measured against a frozen answer key, and the key doesn't move.

Every ticket-and-control pair was labelled by hand before the pipeline ran, and labels are never edited toward the model. Continuous integration refuses a change that pushes any figure below a floor, and refuses results that are older than the prompts, rubrics or retrieval code that produced them.

Gap recall is the floor that matters: a missed deficiency is the failure that costs a certification. Then it happened again, one level up

Re-running the same code eight days later returned 0.926 agreement instead of 0.956, and false positives of 0.065 instead of 0.022. Nothing in the repository had changed that could explain it: the inputs were committed before the original run, the retrieval change since was a refactor on a branch that is not taken, and the vector store held exactly the 89 chunks the corpus produces.

One pair settled it. A ticket judged satisfied on 3 September came back deficient in all four runs on 11 September. The corpus, the rubrics and the answer key are frozen and committed. The model is not, and cannot be - it is served, not installed. Across nine runs the original result turned out to be the most favourable of them, which is not something worth publishing as a single number. Every results file now records which model produced it.

v1's single-call judge reproduced to three decimals over the same window while this agent moved nine pairs. The difference is call count: three to five model calls per pair against one. The verify loop does not buy accuracy. It buys the review queue, and it buys variance.

The same exercise found two rubrics that let a planted deficiency be finalized as compliant, with the verifier agreeing and nothing in the review queue - the worst failure this system has, in three of nine runs. Both were rubrics that said what counts without saying what does not: one accepted a fleet-wide patch rollout as a preventive measure when the rollout is the remedy, the other accepted an outbound "the work is done" email as client acknowledgement. Both are closed, in YAML rather than Python, and both runs since show zero such misses.

05 Cost & speed

Five and a half minutes, eleven cents, and one slow provider.

An audit-readiness pass over twenty service records against nine controls is 180 judgements. Measured end to end on a warm process with four workers, it takes 5 minutes 29 seconds and costs $0.118 — about two thirds of a cent for six judgements. The first pair of a cold process is slower than the rest because the embedding model loads; every figure here is measured after that, because quoting the cold pair as "per pair" would be dishonest.

What it gets wrong, and in which direction

Every disagreement with the answer key is in the strict direction: two pairs called a partial a gap, two called a satisfied a gap, and none called a gap satisfied. An over-strict compliance tool wastes a reviewer's afternoon. An over-generous one loses a certification. If this system has to be wrong, this is the direction to be wrong in.

Of the 46 pairs it declined to finalise in that run, 27 were parked because the citation did not resolve while the second pass agreed with the verdict entirely. Fifteen were a genuine disagreement between the two passes, and four were verdicts that moved between attempts. So the review queue is mostly a citation-discipline queue: the judge reaching the right answer and failing to point at the record. That is also why fewer than half the parked pairs turn out to have been wrong.

One number needs its context stated. The evaluation set is 68 pairs a human labelled, and on it the system parks 10.3%. On the full unfiltered sweep above — every record crossed with every control, including the many combinations nobody would ever ask about — it parks 25.6%. Both are true and they answer different questions. A screenshot of a real run shows 46 parked pairs, so that is the number quoted beside one.

06 Adversarial input

The attack surface is the evidence, not the chat box.

Prompt-injection demos usually assume a hostile user typing into a prompt. In audit work the realistic threat is different: a record written by someone else, months ago, that the pipeline is obliged to read. A vendor changelog pasted into a ticket comment. A supplier's email.

The test corpus contains exactly that - a comment carrying IGNORE ALL PREVIOUS INSTRUCTIONS and an instruction to mark the control satisfied. Records are walked field by field before they reach the model; the hostile span is quarantined in place, the surrounding legitimate evidence is preserved, and the quarantine is surfaced as a security finding on the report rather than swallowed. The verdict on that control stayed gap.

07 Deployment

Your evidence stays inside your network.

Compliance records are the last thing an organisation wants to paste into a hosted tool. AuditReady ships as a container with the embedding model baked in and offline, so retrieval and indexing make no outbound calls at all. The only egress is the language model endpoint - and that endpoint is a configuration value.

Point it at a model you host, and nothing leaves the boundary. There is one place in the codebase that talks to a provider, which is what makes that swap a single environment variable instead of a refactor.

Self-host with your own model endpoint
# clone, configure, run
git clone https://github.com/gauravthorath/audit-ready.git
cp .env.example .env
docker compose up

# bring your own endpoint - nothing reaches a vendor API
AUDITREADY_LLM_BASE_URL=http://vllm:8000/v1
AUDITREADY_MODEL=Qwen/Qwen2.5-7B-Instruct

# or run a headless report straight to Markdown + JSON
uv run python audit/batch.py --pack assistant/data/checklists/iso27001.yaml

Air-gapped retrieval

Sentence-transformer weights are built into the image and the hub client runs in offline mode. Indexing 20 tickets produced 89 chunks with the network unavailable.

Runs unprivileged

Non-root by default, a health check the orchestrator can read, and a named volume so the vector store survives a restart instead of re-indexing on every boot.

204 tests that need no API key

The whole unit suite runs offline in about five seconds and gates every push, alongside a check that the engine core stays free of framework imports.

08 What this is not

Read this before you consider it for real evidence.

A compliance tool that oversells itself is a liability for whoever adopted it. Every limit below is a real constraint on today's build, not a modesty note - and each one is the honest answer to a question a procurement review would ask.

Not validated on real data

Every figure on this page comes from a synthetic corpus written for the project - 20 tickets, 7 change records, 10 email threads. No client or employer material is involved, and no result here predicts performance on your records.

Not a certification

The tool prepares and cites evidence for a human auditor. It does not certify anything, it does not replace an audit, and nothing it outputs should reach a certifying body without a person having reviewed it.

Not the standard's text

Controls are own-worded paraphrases of clause intent, written for this project. They are not the text of ISO 9001 or ISO 27001 and are not a substitute for the standards, which are copyrighted.

Fifteen controls, not a full clause set

Nine ISO 9001 controls and six ISO 27001 controls. Enough to prove that a standard is configuration rather than code; nowhere near a complete audit scope for either standard.

One live connector

GitHub Issues over MCP, Jira REST, Linear GraphQL, exported mail, plus offline CSV and JSON import. Live Gmail or Outlook mailbox access is deferred deliberately: it needs a consent and privacy design, not just an API token, so the human exports the threads that are evidence.

No support contract

This is a portfolio-grade project by one engineer, not a vendor relationship. There is no SLA, no data-processing agreement and no professional indemnity behind it. Treat it as software you evaluate, not software you buy.

09 Verification

The code is the argument.

A compliance tool asks for an unusual amount of trust: it reads your internal records and tells you what an auditor will find. "Trust our accuracy claims" is not a reasonable thing to ask, so none of it is asked here. The evaluation harness, the answer keys, the rubrics and the failures all live in the public repository, and every number on this page is reproduced by one command against a frozen key. Clone it, watch it run, change a prompt, and see the gate reject the regression.

The corrections on this page are not editorial hindsight. Each one has a commit behind it: the prompt fix, the grader swap, the headline number deleted from the README. They were written down while the work happened - in a dated journal kept from the first commit - and the repository history carries the same trail.

Open source

The engine, the agent, the connector layer, the eval harness and the gate - plus the Docker setup used for the numbers on this page. Apache-2.0 on GitHub; clone and run it yourself.

Reproduce the numbers

The corpus, the frozen answer keys and the committed results.json sit together in the repository. One command re-runs the whole evaluation, and CI refuses results older than the code that produced them.

Add your standard

A new standard is a YAML file of controls and rubric conditions. Writing one for ISO 20000 or CMMI needs no code change, and your criteria text stays yours.
